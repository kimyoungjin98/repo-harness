# 레포지토리 하네스 구성

- 배포에 포함된 `references/rules/`가 기본 규칙이며, 별도 원본 저장소 없이 실행 가능. 작성자가 관리하는 원본은 저장소의 `docs/`
- 대상 프로젝트를 조사하고, 규칙을 해당 프로젝트에 맞게 반영한 뒤 검증까지 진행
- CLI나 다른 스킬 설치 없이 에이전트의 파일 읽기·쓰기와 사용 가능한 로컬 도구로 구성
- 구성 요청은 하네스 문서 작성 범위. 앱 제작, 의존성 설치, 브랜치 생성, CI 변경, PR 생성, 알림 전송은 별도 요청 없이 실행하지 않음

## 원본과 대상 확인

- 스킬 경로는 이 `SKILL.md`가 있는 디렉터리. 심볼릭 링크로 등록되어 있으면 실제 파일 위치를 기준으로 확인
- 대상 경로는 사용자 지정 경로를 우선하고, 지정이 없으면 현재 작업 중인 프로젝트 사용
- [원본 경로와 갱신 기준](./references/update.md)을 읽고 기존 설치와 원본 경로를 확인
- 최초 구성은 이 스킬의 `references/rules/`를 사용. 사용자가 외부 원본을 지정했거나 이전에 외부 원본 사용을 기록한 경우에는 해당 경로를 사용
- 아래 링크는 포함된 규칙 기준. 외부 원본 모드에서는 동일한 파일명을 외부 경로에서 찾아 읽음
- 설치 대상이 원본 문서 폴더나 스킬 폴더 자체인 경우 덮어쓰지 않음. 대상 프로젝트 내부에 스킬이 설치된 일반적인 경우에는 설치된 스킬 파일을 보존하고 프로젝트 문서만 구성
- 포함된 규칙이 누락되거나 manifest 해시가 다르면 불완전한 설치로 보고 재설치를 안내. 외부 원본 경로 입력을 기본 요구사항으로 만들지 않음

## 참조 문서

- 항상 [워크플로우](./references/rules/main.md), [공통 규칙](./references/rules/code-base.md), [테스트](./references/rules/test.md), [브랜치 전략](./references/rules/git-branch.md)을 읽음
- 프론트엔드가 있으면 [프론트엔드 규칙](./references/rules/code-base/front-end.md)과 [디자인 시스템](./references/rules/code-base/design-system.md)을 읽음
- 백엔드가 있으면 [백엔드 규칙](./references/rules/code-base/back-end.md)을 읽음
- 설치 결과 검증 시 [하네스 평가](./references/rules/evaluation.md)의 관련 시나리오 확인
- 대상에 기록할 정보는 [프로젝트 설정 양식](./assets/project.md)을 참고
- 규칙을 충돌 없이 적용할 수 없는 부분만 사용자에게 확인. 기존 기술과 규칙을 우선한다는 원칙은 질문 없이 적용

## 프로젝트 분석

- 대상의 `AGENTS.md`, 하위 영역의 지침, README, 패키지와 워크스페이스 설정, CI, 테스트 설정, Git 상태를 확인
- 프론트엔드·백엔드·모노레포 여부, 언어와 도구, 패키지 매니저, 앱과 공통 패키지 경로를 파악
- 검증 명령은 실제 스크립트나 설정에서 확인하고 근거 경로를 기록. 관례만으로 명령을 생성하거나 통과를 추정하지 않음
- 모노레포는 앱과 패키지별 실행 위치 및 영향 관계를 구분
- 기준 브랜치는 기존 전략과 로컬 Git 정보로 확인. 구성 중 확정할 수 없으면 미확정으로 기록하고, 실제 브랜치 작업 전에 확인하도록 명시
- Git 저장소가 아니어도 문서 구성은 진행하고 Git·PR 항목은 미구축으로 기록. `git init`을 자동 실행하지 않음
- 비어 있는 프로젝트는 구조 미정으로 기록하고 기본 기술은 후보로만 제시. 앱이나 테스트 환경을 생성하지 않음
- 분석에 필요한 정보만 읽고 인증정보나 환경변수 값을 문서로 복사하지 않음

## 문서 구성

기존 하네스 문서 위치가 있으면 재사용하고, 없으면 `docs/harness/`를 사용한다. 아래는 기본 배치다.

```text
대상 프로젝트/
├── AGENTS.md
└── docs/harness/
    ├── project.md
    ├── main.md
    ├── code-base.md
    ├── code-base/
    │   ├── front-end.md
    │   ├── back-end.md
    │   └── design-system.md
    ├── test.md
    ├── git-branch.md
    ├── evaluation.md
    └── .harness-state/      # 원본 경로, 해시, 이전 생성 기준
```

- 원본의 `main.md`, `code-base.md`, `code-base/`, `test.md`, `git-branch.md`, `evaluation.md`를 위 구조로 반영하되 대상에 맞게 조정
- 링크 보존을 위해 규칙 문서 묶음을 함께 배치. 적용하지 않는 영역은 `project.md`에 비적용으로 표시하고, 해당 파일에는 비적용 사유만 남겨도 됨
- `project.md`에 실제 기술, 영역별 경로와 검증 명령, 기준 브랜치, 문서 위치, 적용하지 않는 규칙, 미확정 항목을 기록
- 원본 모드(`bundled` 또는 `external`)와 경로를 `project.md`에 기록. 포함된 규칙은 manifest의 해시로 버전을 확인하며, 설치 대상 프로젝트의 Git 커밋을 스킬 버전으로 기록하지 않음. 이전 생성 기준은 [갱신 기준](./references/update.md)에 따라 보존
- 기존 기술과 다른 신규 구성 기본값은 적용 규칙으로 복사하지 말고 기존 기술을 명시. 설치만을 위해 기술을 변경하지 않음
- `test.md`에는 프로젝트의 실제 검증 명령과 실행 위치를 연결. 설정이 없는 검사는 미구축으로 구분
- `git-branch.md`에는 기존 전략을 반영하고, `develop`이 없다고 새로 만들지 않음
- 원본 `main.md`의 `Skills 활용`, `AGENTS.md`, `여러 프로젝트별 구축 필요`는 베이스 유지관리 항목이므로 대상의 운영 절차로 복사하지 않음. 대신 대상의 `project.md`, 루트 `AGENTS.md`, 설치된 `evaluation.md` 참조를 연결
- 문서가 다른 위치로 이동한 경우 모든 상대 링크를 새 위치 기준으로 수정

## AGENTS.md 연결과 재실행

- 원본 저장소의 `AGENTS.md`는 복사하지 않음. 대상의 기존 내용을 보존하고 아래 경계로 구분한 하네스 참조 블록만 추가 또는 갱신
- 경계 블록이 여러 개이거나 닫히지 않았으면 자동 교체하지 않고 확인. 기존 본문과 하네스 규칙의 충돌은 기존 규칙을 우선하여 정리
- 재실행 시 같은 블록이나 파일을 중복 생성하지 않음. [갱신 기준](./references/update.md)에 따라 이전 생성본·현재 문서·새 생성 후보를 비교하고, 사용자 수정과 원본 변경을 함께 반영
- 이전 생성본이 없으면 기존 문서를 사용자 문서로 보존. 같은 규칙이 양쪽에서 다르게 바뀐 경우에만 선택을 확인하고, 충돌이 남아 있으면 문서와 설치 상태를 갱신하지 않음
- 하위 `AGENTS.md`가 상위 규칙과 충돌하는 경우 해당 영역의 적용 범위를 `project.md`에 명시하고 하위 지침을 무조건 덮어쓰지 않음
- 상대 링크는 기본 경로가 아닌 실제 설치 위치 기준으로 작성

```markdown
<!-- repository-harness:start -->
## 레포지토리 하네스

- 작업 시작 시 [프로젝트 설정](./docs/harness/project.md)과 [워크플로우](./docs/harness/main.md)를 확인
- 코드 변경은 [코드 베이스 규칙](./docs/harness/code-base.md), 검증은 [테스트](./docs/harness/test.md), 브랜치 작업은 [브랜치 전략](./docs/harness/git-branch.md)을 적용
- 사용자 요청과 기존 프로젝트 규칙을 우선하고, 현재 작업에 필요한 단계만 진행
<!-- repository-harness:end -->
```

## 검증과 완료

- 생성하거나 수정한 문서의 상대 링크가 모두 실제 파일을 가리키는지 확인
- `project.md`에 적힌 명령과 경로가 실제 설정에 존재하는지 확인. 실행하지 않은 명령은 실행 검증 미실행으로 기록
- 가능하면 `git diff --check`로 공백 오류를 확인하고, 작업 전 상태와 비교하여 기존 변경이 보존되었는지 검토
- 재실행 시 기존 연결 블록과 사용자 수정이 보존되는지 확인. 실제 재실행하지 않았다면 실행 통과로 보고하지 않음
- 하네스 구성만으로 앱 전체 테스트·빌드·DB 마이그레이션을 실행하지 않음. 관련 코드 변경이나 별도 요청이 있을 때 설치된 테스트 규칙 적용
- 생성 파일, 적용한 기술과 규칙, 검증 결과, 미구축·미확정 항목을 보고
- 문서 연결과 확인 가능한 구성 검증이 끝나면 하네스 문서 구성 완료로 보고. 앱 검증이나 외부 자동화까지 완료한 것으로 보고하지 않음

## 사용 예시

```text
$repository-harness 이 프로젝트에 레포지토리 기반 하네스를 구성해줘.
$repository-harness /path/to/project에 기존 기술과 AGENTS.md를 유지하면서 구성해줘.
$repository-harness 기존 하네스를 현재 규칙으로 갱신하고 프로젝트별 수정은 유지해줘.
$repository-harness 규칙 원본은 /path/to/repository-harness이고, 대상은 /path/to/project야. 하네스를 구성해줘.
```

- 스킬 목록에 등록되지 않은 환경에서는 이 `SKILL.md`의 실제 경로를 에이전트에게 전달하여 읽고 실행하도록 요청 가능
- CLI로 설치한 후 기본 호출만으로 구성 가능. 규칙 원본 경로 지정은 외부 원본을 사용하려는 경우에만 필요
- 스킬을 업데이트한 뒤 하네스 갱신을 요청하면 최신 포함 규칙으로 기존 문서를 병합. 스킬 설치나 업데이트 자체가 대상 프로젝트의 하네스 구성을 실행하는 것은 아님
- 작성자는 `docs/` 변경 후 배포용 규칙을 생성하고, 구성 절차는 이 파일에서, 생성 문서 양식은 `assets/project.md`에서 관리
