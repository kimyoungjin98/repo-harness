# 레포지토리 기반 하네스 구축 계획

## 목표와 작업 권한

- 에이전트 워크플로우로 코딩을 자동화하고, 개발자는 업무 요청 후 PR을 검토하는 구조를 목표로 함
- 구현·수정 요청은 요청 범위의 조사, 계획, 파일 수정, 필요한 의존성 설치, 검증, 별도 Worktree와 작업 브랜치 생성, 커밋, 해당 원격 작업 브랜치로 push, PR 생성·갱신까지 포함. 각 단계의 진행 여부를 다시 묻지 않음
- 사용자 요청이나 프로젝트 규칙이 작업 범위를 제한하면 해당 제한을 우선 적용. 조사·리뷰만 요청한 경우 파일 수정이나 PR 생성을 임의로 진행하지 않음
- 이미 확인한 권한과 프로젝트 설정은 같은 범위의 후속 작업에도 적용. 에이전트가 문서·코드·설정으로 확인할 수 있는 내용은 직접 확인하며, 진행 상황 공유를 승인 대기로 바꾸지 않음
- 구현 방식과 검증 방법은 기존 규칙과 코드로 결정하고, 선택 근거는 PR에 기록. 답변 없이는 기대 동작을 정할 수 없는 정책, 요청 범위 밖의 작업, 기존 작업을 잃을 수 있는 조작만 필요한 내용을 모아서 확인
- merge, 배포, 운영 데이터 변경, 강제 push, 사용자 변경 삭제는 일반 구현 요청에 포함하지 않음
- PR 알림은 사용자가 전송을 요청했거나 프로젝트에 전송 대상과 자동 전송 권한이 정해져 있으면 해당 범위에서 실행. URL이나 인증정보가 있다는 사실만으로 전송 권한을 추정하지 않음
- 하네스의 작업 권한과 CLI 실행 환경의 권한은 구분. 환경이 요구하는 승인은 문서로 우회하지 않으며, 막힌 명령·사유·필요한 설정을 보고. 사용자 전역 권한 설정은 임의로 변경하지 않음

## 규칙 적용 순서

- 사용자 요청과 기존 프로젝트 규칙을 우선하고, 프로젝트 override는 공통 하네스 규칙보다 우선 적용
- 프로젝트 하네스가 구성된 경우 작업 시작 시 `project.md`에 기록된 override 목록과 적용 범위를 확인하고, 현재 작업에 해당하는 override를 공통 규칙과 함께 읽음
- override가 대체하거나 비적용으로 지정한 공통 규칙은 함께 적용하지 않음. 지정하지 않은 부분은 공통 규칙을 적용
- 공통 규칙과 다르다는 이유만으로 override를 무시하거나 선택을 다시 묻지 않음. override끼리 충돌하거나 대상과 적용 범위가 불명확하여 판단할 수 없는 부분만 확인
- 대상 프로젝트의 공통 하네스 문서는 한 벌만 유지하고 프로젝트별 차이는 override와 `project.md`에 기록. 갱신 상태는 경로와 해시만 보존하며 `baseline/` 등 문서 본문의 기준 사본은 생성하지 않음

## 시작하기 전

- Git CLI, 대상 저장소와 원격 인증, PR 생성 인증, Discord 또는 Slack Webhook 연동은 하네스 구성의 필수 조건
- 구성과 갱신 전에 필수 연동을 확인. 미준비 또는 미확인 항목이 있으면 필요한 조치를 모아서 안내하고 구성·갱신은 준비 대기로 보고
- 문서 구성만 요청된 경우에도 필수 연동을 생략하거나 비적용으로 바꾸지 않음. 조사와 기존 문서 확인은 진행할 수 있지만 필수 연동 확인 전 새 하네스 적용과 완료 처리는 보류

- 인증정보와 Webhook URL 원문은 문서에 기록하지 않고 환경변수나 기존 비밀정보 저장소에서 관리. 문서에는 설정 이름과 준비 상태만 기록
- 준비 상태 확인을 위해 임의로 push, PR 생성, Webhook 테스트 전송을 실행하지 않음
- 설치·로그인·외부 연동이 필요한 경우 필요한 조치를 안내하고, 이미 준비된 항목은 다시 설정하지 않음
- Webhook은 URL 보유만으로 연동 완료로 판단하지 않음. PR 생성 이후 알림을 실행할 명령·스크립트·자동화 또는 사용 가능한 전송 도구와 설정 연결까지 확인
- 기존 전송 경로가 없으면 스킬에 포함된 기본 스크립트 사용. 준비와 실행 기준은 [Discord·Slack 알림](./notifications.md) 적용
- 설정 확인과 실제 전송 성공은 구분. 시험 전송 권한이 없으면 설정 확인 근거와 전송 검증 미실행을 기록

## 프로세스

### 사용자 요청 (프롬프트)

- 사용자가 CLI로 작업을 요청하는 단계
- 단순 작업일 경우 바로 진행
- 복잡하거나 단위가 큰 작업은 아래 항목을 중심으로 사용자 요청과 기존 문서·코드에서 구현의도를 파악
  1. DB 스키마 작성/수정/삭제
  2. 서비스 로직 작성/수정/변경
  3. 모듈 제작 및 구현
  4. (프론트의 경우) api -> response -> page 등의 데이터 fetch 아키텍처 구성
  5. 2 ~ 3 단계 뎁스가 들어가는 모듈이나 서비스 로직 구현
  6. 여러 페이지나 컴포넌트를 거치는 로직
- 작업 종류만으로 질문하지 않고 사용자 요청, 기존 코드, 문서로 결정할 수 있는 부분은 바로 진행
- 구현에 필요한 정책이나 동작을 결정할 수 없을 경우 사용자에게 필요한 질문을 모아서 확인
- 답변이 필요한 부분은 보류하고, 답변과 무관한 조사나 검증은 진행 가능
- 완료 조건 : 요청 범위, 기대 동작, 추가 확인이 필요한 부분이 구분되어 있음

### 구현 계획

- 사용자의 요청대로 구현 할 계획을 작성하는 단계
- 고려 해야할 사항
  1. 기대 동작과 변경 범위
  2. 기존 구조와 재사용할 코드
  3. DB, API, 공통 타입 등 다른 영역에 미치는 영향
  4. 검증 명령과 통과 기준
  5. 변경에 따른 문서 반영과 실패 시 대응
- 단순 작업은 별도 계획 파일 없이 간단히 정리하고 진행
- 완료 조건 : 변경 대상과 검증 방법이 정해져 있고, 구현에 필요한 미확정 사항이 해소되어 있음

### 구현

- 사용자의 의도에 맞게 구현하는 단계
- 에이전트 위임은 사용자 요청이나 적용되는 프로젝트 규칙에 따라 사용
- 파일 수정 전에 [Git 브랜치 전략](./git-branch.md)에 따라 별도 Worktree와 작업 브랜치를 준비하고 경로·브랜치를 확인. 문서나 단순 수정도 생략하지 않으며, 준비 실패 시 원래 작업 공간에서 수정하지 않음
- 구현·검증·커밋은 확인된 Worktree에서 진행하고 원래 작업 공간은 보존. 작업 시작 전 기존 변경사항을 확인하고, 사용자 변경사항은 임의로 되돌리거나 커밋하지 않음
- 요청과 관련 없는 리팩터링이나 기술 변경은 포함하지 않음
- 완료 조건 : 계획한 동작이 구현되어 있고, 변경 내역을 확인할 수 있음

### 완료

#### Pull Request

- Git CLI로 변경사항을 관리하고, PR은 해당 호스팅 서비스의 CLI 또는 API 활용
- 대상 프로젝트에서 구현 작업이 완료되고 필수 검증이 통과하면 PR 생성
- 평가나 검토만 요청된 작업은 PR 생성 대상에서 제외
- 위 작업 권한과 프로젝트 설정에 따라 커밋·push·PR 생성을 연속 진행. 이미 허용된 작업에 별도 승인을 다시 요청하지 않음. 실행 환경이 승인을 요구하는 경우 diff, 검증 결과, PR 제목과 본문을 준비한 뒤 해당 명령의 승인 절차 적용
- 인증 실패 시 PR 생성만 중지하고, 완료한 작업과 검증 결과를 보존한 뒤 인증에 필요한 조치를 안내
- 네트워크 오류는 일시적인지 확인하고 재시도하되, PR 생성 여부를 조회하여 중복 생성을 피함
- 재시도 후에도 실패하면 원인, 현재 브랜치, 남은 작업을 보고
- 작성 요령
  1. 제목
  2. 작업한 내역 요약
  3. 리뷰할 때 중점적으로 검토해야 할 부분
  4. 구현 근거
  5. 체크 리스트
- 완료 조건 : PR 링크와 검증 결과를 보고했음. PR 생성 실패 시 구현 완료와 PR 생성 대기를 구분하여 보고
- PR 생성은 merge나 배포 권한을 포함하지 않음
- PR 생성 후 필수 연동으로 확인한 Discord 또는 Slack에 프로젝트에 정해진 전송 권한으로 PR 링크와 검증 결과 알림 전송
- 전송 실패 시 PR 생성 성공과 알림 실패를 구분하고, 알림까지 완료된 것으로 보고하지 않음

#### 문서화

- [문서작성](./document-write.md)
- 동작이나 정책에 영향을 주는 문서는 구현과 같은 PR에 반영
- 날짜별 작업 이력과 도메인 정책 문서의 위치는 대상 프로젝트의 기존 구조를 우선
- 별도 구조가 없으면 작업 이력은 `docs/history/YYYY-MM-DD.md`, 도메인 정책은 `docs/plan/[도메인명].md` 사용
- 기록 항목과 정책 변경 이력은 문서작성 규칙을 적용하고, 같은 날짜의 작업은 기존 파일에 추가
- 이력에는 제안 또는 반영 상태를 구분하고, merge 전에는 배포된 정책으로 기록하지 않음
- merge 이후 기록 갱신이 필요한 프로젝트는 merge 이벤트로 실행되는 CI 등 별도 자동화로 처리
  - 실행 주체, 갱신할 문서, 중복 실행 방지 기준, 실패 확인 방법을 해당 프로젝트에 기록
  - 자동화가 없으면 후속 작업으로 보고하고 자동 갱신을 약속하지 않음
- 완료 조건 : 변경된 동작과 정책이 문서에 반영되어 있고, 후속 작업이 필요한 경우 담당 주체와 실행 조건이 기록되어 있음
